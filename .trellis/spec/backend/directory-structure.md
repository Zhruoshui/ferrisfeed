# Directory Structure

> How backend (Rust) code is organized in this Flutter + flutter_rust_bridge project.

---

## Overview

The Rust crate lives in `rust/` and is consumed by Flutter through flutter_rust_bridge (FRB). The architecture follows a thin-API-over-services split: `api/*.rs` files are the only modules exposed to Dart; all business logic, persistence, and I/O live in non-exposed modules (`db/`, `feed/`, `services/`).

---

## Directory Layout

```
rust/
├── build.rs                 # Android x86_64 clang_rt.builtins fix (FRB #1719)
├── Cargo.toml               # flutter_rust_bridge (pinned rev 254b193), chrono, serde, ...
├── src/
│   ├── lib.rs               # pub mod api; mod frb_generated;
│   ├── frb_generated.rs     # auto-generated by FRB (do not edit)
│   └── api/                 # FRB-exposed layer (thin wrappers)
│       ├── mod.rs           # module declarations + re-exports (AppError)
│       ├── error.rs         # AppError enum — project-wide error type
│       ├── types.rs         # shared DTOs: Feed, Entry, Category, SyncProgress, ...
│       ├── app.rs           # init_app() [#frb(init)], greet(), app_version()
│       ├── reader.rs        # TODO(P1a): remove — legacy JSON-snapshot prototype
│       ├── feed.rs          # (P0b) feed CRUD; (P1a) subscribe + sync
│       ├── entry.rs         # (P0b) entry list/get/mark-read/star; (P1a) search
│       └── settings.rs      # (later) settings get/set
│   ├── db/                  # (P0b) rusqlite pool, schema, migrations, repositories
│   ├── feed/                # (P1a) fetch (reqwest) + parse (feed-rs)
│   └── services/            # business logic the api layer delegates to
├── migrations/              # (P0b) vN_name.sql files ported from Livo
```

## Module Organization

### `api/` — FRB boundary (thin)

- **Only** `api/*.rs` files are codegen-exposed to Dart.
- Each function in `api/` should (de)serialize DTOs and delegate to `services/` or `db/`.
- Keep blocking I/O and multi-row DB work **out** of `#[frb(sync)]` functions (they run on the Dart UI isolate). Use plain `pub fn` (worker pool) or `async fn` + `spawn_blocking_with` for DB access.

### Sync vs async policy

| Flavor | Runs on | Use for |
|--------|---------|---------|
| `#[frb(sync)]` | Dart main isolate | Tiny pure lookups (<1ms): `app_version`, `greet`, indexed PK lookups |
| plain `pub fn` | FRB worker pool | Short blocking work (single DB query) |
| `async fn` | Tokio runtime | HTTP fetch + DB compose; use `spawn_blocking_with` for the DB touch |

### Non-exposed modules

- `db/` — rusqlite connection pool, schema migrations, repository structs. Never directly called from Dart.
- `feed/` — HTTP fetching (reqwest) and XML parsing (feed-rs). Called from `services/`.
- `services/` — business logic orchestrating `db/` + `feed/`. Called from `api/`.

## Naming Conventions

- Rust module/file names: `snake_case`.
- FRB converts `snake_case` Rust to `camelCase` Dart automatically.
- Enum variants that collide with Dart keywords get a trailing `_` in generated Dart (e.g. `External` → `external_`). Keep the Rust name clean.
- DTO structs derive `Debug, Clone, Serialize, Deserialize`.
- Timestamps use `chrono::DateTime<Utc>` (FRB `chrono` feature maps to Dart `DateTime`).

---

## Codegen workflow

Run `./scripts/frb.sh` (or `flutter_rust_bridge_codegen generate`) after **every** change under `rust/src/api/**`. Generated files (`frb_generated.rs`, `lib/src/rust/frb_generated*.dart`, `lib/src/rust/api/*.dart`) are committed and must stay in sync.

`flutter_rust_bridge.yaml` pins `auto_upgrade_dependency: false` and rev `254b193` — do not change.

## FRB codegen gotchas

> **Gotcha — enums with field data require `freezed`.** FRB generates any Rust
> `enum` whose variants carry field data (e.g. `AppError::Network { url, status, message }`)
> as a `@freezed sealed class` in Dart. That requires `freezed_annotation`
> (dependency) + `freezed` and `build_runner` (dev_dependencies) in `pubspec.yaml`.
> Without them the generated Dart won't compile. Any new field-carrying enum
> triggers this; the deps are already present after P0a.

> **Gotcha — `pub(crate)` for signatures FRB can't codegen.** FRB cannot codegen
> functions/constructors whose parameters use `impl Into<String>` (or other
> `impl Trait`) — codegen fails on them. Mark such helpers `pub(crate)` so FRB
> ignores them entirely (e.g. `AppError::not_found(...)`, `invalid_input(...)`,
> `database(...)`). Public API functions must use concrete types (`String`, not
> `impl Into<String>`).

> **Gotcha — Android x86_64 emulator needs a `build.rs` link fix.** Bundled
> SQLite (and FRB itself) fails to `dlopen` on Android x86_64 emulators with
> `cannot locate symbol "__extenddftf2"` (FRB #1719) — a `clang_rt.builtins`
> linking gap. `rust/build.rs` links `clang_rt.builtins-x86_64-android` for that
> target only, with robust NDK path discovery. Physical arm64 devices are
> unaffected. If the emulator breaks after an NDK bump, check `build.rs`.

> **Gotcha — codegen does not delete removed modules.** Deleting a Rust api
> module (e.g. `simple.rs`) leaves its stale generated Dart
> (`lib/src/rust/api/simple.dart`) behind; delete it manually or `flutter analyze`
> fails on the dangling import.

> **Gotcha — FRB keys generated Dart classes by Rust struct NAME, not module
> path.** Two `api/` modules exposing structs with the same name (e.g.
> `types::Feed` and `reader::Feed`) produce a duplicate-Dart-class clash —
> `frb_generated.dart` imports every `api/` module and codegen emits "multiple
> objects with same key". Workaround: expose the type from only ONE module; do
> NOT `#[frb(unignore)]` the duplicate. While `reader.rs` coexists with the new
> persisted APIs, `feed.rs` reuses `reader::Feed` (and `types::Feed` /
> `ArticleViewMode` / `FeedDraft` stay un-`#[frb(unignore)]`'d). P1a removes
> `reader.rs` and switches `feed.rs` to `types::Feed`.

> **Convention — keep third-party crate types out of `api/`.** FRB codegen
> scans `api/*.rs`; if it sees `rusqlite::`, `reqwest::`, `tokio::` types in
> signatures it tries (and fails) to codegen them. Put `From<X> for AppError`
> impls bridging third-party errors → `AppError` in the consuming non-api
> module (e.g. `db/connection.rs` holds `From<rusqlite::Error> for AppError`),
> not in `api/error.rs`. `api/*.rs` should only mention `AppError` + `types::*`
> DTOs in its signatures.

> **Convention — DB init is a separate `pub fn`, not `#[frb(init)]`.**
> `#[frb(init)] init_app()` is called by `RustLib.init()` with no args, so it
> can't receive a DB path. `init_database(path: String)` is a separate plain
> `pub fn` (worker pool) that Dart calls after `RustLib.init()` with a path
> from `path_provider`. Keep `init_app` for FRB-only setup; anything needing
> Flutter-provided data (paths, config) is its own function.

> **Gotcha — FRB async fns already run on a tokio runtime; don't create a
> second one.** FRB v2.12's `DefaultHandler` holds a `SimpleAsyncRuntime`
> wrapping `tokio::runtime::Runtime::new()` (multi-threaded, with I/O driver +
> timer). `wrap_async` spawns the `async fn` body ON that runtime, so you can
> `.await` `reqwest`/`tokio` I/O **directly** inside `async fn` api functions —
> no need to build a separate `OnceLock<tokio::runtime::Runtime>` and
> `handle().spawn(...).await`. (P1a's `feed/runtime.rs` does this redundantly;
> it works but spawns a wasteful second 2-thread runtime — a future cleanup
> should await `*_impl` directly and delete `feed/runtime.rs`.)
